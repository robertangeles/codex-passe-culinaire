## Media, backups and recovery

Media writes belong on the attached disk. Files under other runtime paths are ephemeral. The disk is unavailable during build and pre-deploy, so never put media migration in those commands. Use the service's SSH address and SFTP/SCP for a private transfer; verify Render Singapore's published SSH host fingerprint first. A 135-file media archive was transferred and checksum-checked on 12 October 2026. The temporary archive was removed after extraction.

Render provides point-in-time recovery for paid Postgres and daily snapshots for the disk. Database recovery creates a **new** instance; verify its content before changing `DATABASE_URI` and redeploying. Disk snapshots restore the whole disk and discard later writes. These two recovery points are separate, so compare database media records with recovered files before reopening uploads. See [Render Postgres recovery](https://render.com/docs/postgresql-backups) and [disk snapshots](https://render.com/docs/disks). A paired export from the live database and disk restored successfully into an isolated local database and directory on 12 October 2026: four pages, 15 media records, 135 files and one labelled test enquiry. The temporary local database was dropped after verification. The private exports remain under ignored `.local/render-release/recovery-check/`; a checksum-verified launch copy is stored outside the checkout at `~/Documents/Passe Culinaire Backups/render-launch-2026-10-13/` with owner-only permissions. This copy is a launch recovery point, not a recurring backup of later submissions or uploads. Arrange ongoing storage on a second device or private cloud. Never restore a dump over the live populated database.

For a bad code deployment, use Render's deploy history to redeploy the prior known-good commit only after checking migration compatibility. Check `/api/health`, HTML and media before considering recovery complete. Do not automatically reverse a database migration or overwrite newer content. For a database or disk incident, preserve the current resources, create recovery targets and validate them in isolation first.

Both domains are verified in Render, HTTPS health is 200, and `www` redirects to the root. No second contact email was sent during the cutover.

If the domain must be pointed back to this Render service after a DNS change, use this order:

1. Capture the full DNS zone, especially MX, SPF, DKIM and DMARC. Pause admin edits for the cutover window.
2. Change only the GoDaddy web records: root `@` A to Render's documented `216.24.57.1` and `www` CNAME to `cc-passe-culinaire.onrender.com`; remove conflicting web A/AAAA/forwarding records after reviewing them. Preserve email and Resend records. Keep `NEXT_PUBLIC_SERVER_URL` on the Render address while DNS propagates. Publication jobs send the revalidation secret to that configured origin; changing it before DNS reaches Render would send the secret to the old host.
3. From the Render web service's SSH shell, confirm `passeculinaire.com` resolves to Render's web address and `curl -fsS https://passeculinaire.com/api/health` returns this service's healthy database response with valid TLS. Check Render's custom-domain status too. Only then set `NEXT_PUBLIC_SERVER_URL=https://passeculinaire.com` and complete a reviewed rebuild promptly. The publication worker uses the web service's DNS resolver when sending its bearer secret. Canonical URLs point to the Render address and admin scheduling from the new domain is unavailable during this brief gap, so keep edits paused.
4. Check HTTPS, the `www` redirect, canonical URLs, sitemap, forms, images and admin scheduling on the public domain. Resume edits after these checks. See [Render custom domains](https://render.com/docs/custom-domains) and [DNS configuration](https://render.com/docs/configure-other-dns).
